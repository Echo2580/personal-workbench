# 个人工作台 · JTBD 与 Pre-mortem 双重分析

> **版本**：v1.0 · 2026-10-14
> **定位**：项目开工前的分析基线——先用 JTBD 定义"什么叫成功"，再用 Pre-mortem 预演"会怎么失败"，产出的结论直接进入开工清单。
> **方法**：JTBD（任务陈述【4+2】、Job Story、三层次拆解、可衡量验收标准）；Pre-mortem 五步流程（失败场景 → 原因四维度扫描 → 可能性×严重性矩阵 → 预防措施 → 调整跟进）。

---

## 0. 项目速览

「个人工作台」不是某个问题的解决方案，而是一系列功能的聚合体——每个人的工作台都不尽相同，缺什么，就往里加。第一块拼图是「项目集中 + 启动器」：把散落在各个文件夹里的项目汇成一张清单，每个项目配一条"启动配方"，点一下就能跑起来——让"回顾项目"从负担变成随手。

| 项 | 内容 |
|---|---|
| 项目 | 个人工作台（personal-workbench） |
| 定位 | 功能聚合体；无边界，需求随时加；每人一张自己的台子 |
| 第一块拼图 | 项目集中 + 启动器 |
| 核心痛点 | 项目散落各文件夹 → 存在感低 → 吃灰；回顾要翻文件夹 + 回忆怎么跑，成本高到"回头看看"不会发生 |
| 技术方向 | 本地小管家：Python 常驻小服务 + 本地网页界面（与 FastAPI 学习线重合） |
| 协作 | GitHub 仓库 + Issue 讨论 + PR 提交；联合组员参与 |
| 受众 | 自用核心 + 学编程同学 + 可开源（非简历作品向） |
| 阶段 | 预想阶段：方向已定、尚未写码 |

**分析口径（两层）**：本文档把"被雇佣的对象"分为两层——**工作台本体**（聚合体愿景）与**第一块拼图**（项目集中 + 启动器，当前唯一要落地的切片）。切片的任务必须自己站得住，并被设计成"能被继续加装"的形态。

## 第一部分 · JTBD 分析

### 1.1 雇主识别（谁在雇佣这个项目）

| 角色 | 是谁 | 雇它干什么 | 验收权 |
|---|---|---|---|
| 使用者 · 核心 | 项目发起人本人 | 盘活吃灰项目、随手回顾 + 复用 | 最终验收 =「我持续用不用」 |
| 使用者 · 共建 | 联合组员 | 自己电脑上的项目也集中 + 一键启动 | 共建者兼首批用户 |
| 使用者 · 外部 | 开源受众（学编程的同学等） | 轻量盘点自己的项目 | 用脚投票：clone / star / 离开 |
| 考核方 | 无 | —— | —— |

### 1.2 任务陈述

**（1）工作台本体 · 任务陈述（愿景层）【4+2】**

> 当**一个在学习和工作中不断冒出零散需求的人（核心使用者自己）**在**需要某个小工具帮个忙、却发现它们散落在各个文件夹、工具和网站里**的时候，**他想要**有一张属于自己的、"缺什么就往上加"的台子——需要的东西收在同一处，随手打开就能用，**以便于**日常的零碎麻烦被一张台子持续收拢、越用越顺手；**目前替代方案**是东一个文件夹、西一个小工具地临时凑合，**问题是**：没有"属于自己的聚合入口"——攒不下、接不住、长不大，每换一个场景就要重新折腾一遍。

**（2）第一块拼图 · 任务陈述（切片层）**

**① 核心使用者**

> 当**一个电脑里堆着一批"做完就沉底"练手项目的编程学习者**在**闲下来想回顾老项目、或想把它重新跑起来**的时候，**他想要**一眼看到所有项目都在哪、点一下就能启动，**以便于**那些项目重新"活着"——随时能看、随时能跑，"回顾"不再是件麻烦事；**目前替代方案**是手动翻文件夹找位置 + 凭记忆敲运行命令（或干脆不看），**问题是**：找路径有成本、回忆怎么跑有成本，麻烦一上来，"回头看看"这个动作根本不会发生——项目实际处于"吃灰到底"状态。

Job Story：当我想回顾或重跑一个老项目时，我想要不用翻文件夹、点一下就把它跑起来，以便于项目随时"活着"。

**② 联合组员**

> 当**组员（一起开发这个项目的同学）**在**自己电脑上想收拾自己那摊项目**时，**他们想要**装好工作台、扫自己的目录直接用起来（配方自己配），**以便于**不动公共代码、不麻烦别人，就把自己那摊也盘活；**目前替代方案**是各用各的 IDE Recent Projects / 手动敲命令，**问题是**：工具是大家共建的，不用白不用——但接入成本一高（要改代码、写配置），还不如继续手动，共建成果就只停留在 repo 里。

Job Story：当我自己电脑上项目也散得一批时，我想要装好它、扫自己的目录就用，以便于不重复造轮子就盘活自己那摊。

**③ 开源受众**

> 当**一个刷到（或被安利）这个 repo 的编程学习者**在**同样被"项目散落吃灰"困扰**时，**他们想要** clone 下来几分钟跑通、扫自己目录就用，**以便于**零配置获得"项目集中 + 一键启动"，把吃灰项目救活；**目前替代方案**是手动翻文件夹 / IDE 的 Recent Projects / 干脆不解决，**问题是**：文件夹太散，Recent 只管 IDE 内、还只管"最近"那几个——没有一个轻量工具专门干"把旧项目盘活"这件事。

Job Story：当我也被"项目吃灰"困住时，我想要 clone 下来五分钟跑通、扫自己的目录就用，以便于零配置把旧项目盘活。

### 1.3 竞争集（任务定义的竞争）

凡能完成同一任务的东西都是竞品——包括"凑合着用"和"什么都不做"：

| 替代方案 | 能干到哪一步 | 差在哪 |
|---|---|---|
| 手动翻文件夹 | 找到（靠记忆） | 散、慢，找不到就放弃 |
| 凭记忆敲命令 | 跑起来 | 命令和环境细节会忘，心理门槛高 |
| IDE Recent Projects | 打开（仅 IDE 内） | 只管"最近"；不管非 IDE 项目；没有"一键跑起来" |
| 自记的清单 / 收藏夹 | 记录 | 记录 ≠ 启动，看了还得手动 |
| 什么都不做 | —— | 项目永久吃灰，"回顾"永远不发生 |

### 1.4 三层次拆解（功能 = 及格线 / 情感 = 留存线 / 社会 = 传播线）

| 层次 | 核心使用者 | 组员 | 开源受众 |
|---|---|---|---|
| 功能 | 扫目录 → 清单；一键启动（命令/IDE/文件夹/网页）；自动猜配方 + 一行手改；新项目零接入 | 自己电脑跑通即用；扫自己目录；配方私有、不动公共代码 | clone 即跑；README 说人话 |
| 情感 | 安心（项目"还活着"）；掌控感（心里有数）；回顾的愉悦（"我做过这么多东西"） | 共建的参与感；自己那摊自己说了算 | "就它了"的轻快感——不添负担 |
| 社会 | 小圈子里能说"我自己做了个工具" | 组内谈资："我们做了个这个" | 愿意 star / 推荐："这工具懂我痛点" |

### 1.5 可衡量验收标准

> 原则：像"3 秒内记完一条"一样可测——每条 =「事件 + 数字 + 测法」。以下数字为**启动基线，实测后修订**。

**A. MVP 验收（做出来当场能测）**

| # | 验收点 | 基线 | 怎么测 |
|---|---|---|---|
| 1 | 扫描出清单 | 100 项目量级目录：可用清单 ≤ 5 秒 | 计时实测 |
| 2 | 自动识别率 | 真实项目库：配方自动猜中 ≥ 80%，无需手改 | 实测统计 |
| 3 | 手改兜底 | 猜错的改 ≤ 1 行、≤ 30 秒 | 实测 |
| 4 | 一键启动 | 点主按钮 → 程序跑起来 ≤ 3 秒 | 计时实测 |
| 5 | 新项目零接入 | 往目录丢个新项目 → 0 次手工操作即出现在清单 | 实测 |
| 6 | 组员可用 | 组员在自己电脑 ≤ 30 分钟跑通并接入 ≥ 1 个项目 | 组员实测 |

**B. 持续验收（真正决定"任务是否被完成"）**

| # | 验收点 | 基线 | 怎么测 |
|---|---|---|---|
| 7 | 持续使用（核心） | 上线 2 周内：每周主动打开 ≥ 3 次、至少真启动过 1 个项目 | 自记 / 服务日志 |
| 8 | 推荐意愿（社会层） | ≥ 1 位同学或组员主动说"我也要一个"，或开源后收到 ≥ 1 条正面反馈 | 观察 |

**C. 本体验收（愿景层）**

| # | 验收点 | 基线 | 怎么测 |
|---|---|---|---|
| 9 | 可生长性 | V1 之后新增第一个功能模块时，不改动 V1 已有模块的内部实现（只用挂接） | 开发 v2 时自然验证 |

## 第二部分 · Pre-mortem 分析

### 2.1 设定失败场景

**现在是 2027 年 1 月中旬——个人工作台项目已经彻底失败了。** 具体表现：

1. **仓库停在半成品**：代码最后一次提交停在 2026 年 11 月，没有一个能日常运行的版本；
2. **核心使用者回到老状态**：继续手动翻文件夹，项目继续吃灰，"回头看看"依然不发生；
3. **验收清单形同虚设**：9 条验收标准没有一条留下实测记录；
4. **共建停摆**：组员不再参与，Issue 区冷清，讨论停在开工前。

### 2.2 失败原因清单（四维度扫描 · 17 条）

**需求维度**

| # | 失败原因 |
|---|---|
| R1 | 需求频次被高估："回顾吃灰项目"是低频行为，新鲜劲一过就不再打开 → 工具价值感崩塌 |
| R2 | 范围膨胀：往 V1 塞非启动器功能、或把启动器做过头（GUI 配置器、插件化）；含"为想象中的受众加戏" → 迟迟没有能天天用的成品 |
| R3 | 组员与开源的"需求"是想象出来的：共建热闹一阵后冷清，协作流程空转，仓库变独角戏 |
| R4 | 验收标准不落地：9 条标准躺着没人测，完成度全靠手感 |
| R5 | 口径漂移：把"工作台本体（聚合体）"窄化成"启动器工具"（或反向过宽），方向反复返工 |

**技术维度**

| # | 失败原因 |
|---|---|
| T1 | 复合工程量超预期：常驻服务 + 本地网页 + 进程管理 + 端口/环境细节叠加，学习期自行开发容易陷进泥潭 |
| T2 | "扫描 / 识别 / 启动"的魔鬼细节：配方猜不准、Windows 下启动进程的细节（工作目录、终端窗口、进程善后）、识别规则越堆越难维护 |
| T3 | 过度设计：为"通用"过早抽象（配置校验、插件机制），拖慢 MVP |
| T4 | 复合问题排查能力不足：服务 / 前端联调类问题（CORS、端口、进程）卡住后进度停滞 |
| T5 | 安全与边界失控：一键启动任意命令、扫描范围无边界 → 不敢当日常工具用 |

**场景维度**

| # | 失败原因 |
|---|---|
| S1 | 入口深度倒挂：为省事做的工具，却要"起服务 → 开网页"才能用——比翻文件夹还多一步，自己都懒得开 |
| S2 | 旧方案惯性回潮：IDE 最近项目 + 文件夹快捷方式"其实也能凑合"，新工具一有不顺就回退 |
| S3 | 演示 / 传播落空：想给组员同学展示时，环境依赖让对方跑不起来，传播断在第一公里 |

**习惯维度**

| # | 失败原因 |
|---|---|
| H1 | 收尾不彻底重演：第一版之后没把全部项目接入、没日常化，新鲜感过去就不了了之（与"项目吃灰"是同一个习惯病） |
| H2 | 仪式感取代投入使用：时间花在文档、方法论、仓库装修上，编码迟迟不启动 |
| H3 | 中断即遗忘：停写一段时间后忘了架构细节，重启成本高于放弃 |
| H4 | 协作节奏失控：推进中输出超前于确认、话题失焦，产生返工摩擦 |

### 2.4 预防措施（⚠️⚡ 逐条 · 动作 + 时间 + 负责）

| # | 措施 | 响应 |
|---|---|---|
| R1 | **开工前**先用"最土的办法"验证需求：手搓一份静态项目清单（md + 快捷方式），在真实场景里试一周并记录打开次数；若一周打开 < 2 次 → 触发预案：调整场景打法（把工具优先绑定到更高频的使用时机）。· 负责：发起人 | 预防 + 预案 |
| R2 | **动工前**把 V1 边界写死（扫描 + 清单 + 启动 + 手改兜底）；明确"不做清单"：GUI 配置器、插件机制、云同步、非启动器功能；新想法一律进 Issue 排队，不进 V1。· 负责：发起人 | 预防 |
| R5 | 两层任务陈述（本文档 1.2）冻结为开工基线；开发中每个功能先对照"它服务哪层任务"；每两周复盘一次口径。· 负责：发起人 | 预防 |
| T1 | ① **动工第 1 周内**做"半天 spike"：100 行以内原型，只验证"扫描 + 识别 3 类项目 + 启动"；② 分层交付：先 CLI 最小闭环，再上网页界面。· 负责：发起人 | 预防 + 减轻 |
| T2 | 识别规则先只支持 3–5 种高频类型，其余走"手改一行"兜底；Windows 进程细节（工作目录 / 终端窗口 / 善后）在首次自测时集中踩掉并记录进 devlog。· 负责：发起人 | 减轻 |
| S1 | 入口死磕"一步"：封装"双击即用"脚本（起服务 + 自动开浏览器）；设计基线：从"想用"到"用上" ≤ 2 次操作。· 负责：发起人 | 预防 |
| H1 | 首版可用当天，把自己全部项目接入（先吃自己的狗粮）；两周后跑"持续使用"自测（每周打开 ≥ 3 次）。· 负责：发起人 | 预防 |
| R3 | 组员先当"共建测试者"：首版请 1 位组员实跑（对应验收 №6）；协作降门槛——小改动直接 PR，不搞仪式；若确实冷清：接受"单人核心 + 开源随缘"定位，不因冷清否定项目。· 负责：发起人 + 组员 | 减轻 + 预案 |
| R4 | 9 条验收做成开工清单 checklist；每个版本发布前实测一遍并留记录。· 负责：发起人 | 预防 |
| T3 | 抽象法则：同类需求第二次出现前不抽象；配方格式保持"人可读"级别，不上校验器。· 负责：发起人 | 预防 |
| T4 | 卡壳超 1 小时：先写清"现象 + 自己的判断 + 试过什么"再求助；每个坑写进 devlog。· 负责：发起人 | 减轻 |
| T5 | 启动前展示"将要执行的命令"供确认；扫描范围白名单化（只扫指定目录）。· 负责：发起人 | 减轻 |
| S2 | 与旧习惯并行两周，对比"找到并打开一个项目"的耗时；目标定位为"回顾 / 盘点场景的最优解"，不追求全面替代；接受共存。· 负责：发起人 | 减轻 + 知情接受 |
| H2 | 动工日期与第一周产出写死：一周内出最小可用版；方法论文档到此为止，交付后全部精力转入实现。· 负责：发起人 | 预防 |
| H4 | 确立"单线推进"协作节奏：一次一个话题、确认后再进下一步、不抢跑输出。· 负责：全体 | 预防 |

> ✓ 级两项采取低成本习惯动作：S3（传播暂不设指标，知情接受）、H3（开发结束写 devlog + 维护"架构一页纸"，回来先读它）。

### 2.5 调整与跟进

**开工前必做 5 件事**（本次 Pre-mortem 的直接产出）：

| # | 动作 | 对应风险 |
|---|---|---|
| 1 | 土办法需求验证（静态清单试一周，记录打开次数） | R1 |
| 2 | 写死 V1 边界与"不做清单"（进 README / Issue） | R2 |
| 3 | 冻结两层任务陈述（本文档 1.2） | R5 |
| 4 | 半天 spike：扫描 + 识别 + 启动原型 | T1 |
| 5 | 入口方案定稿："双击即用" ≤ 2 次操作 | S1 |

**监控指标**：9 条验收标准（每个版本发布前实测留档）；每周使用自测（打开次数、真实启动次数）。

**重做时机**：开工前（本文档）→ 首版发布后 2 周 → 需求变更时 → 每月常规回顾。

**收尾对账**：上线 1 个月后做 Post-mortem，与 2.2 清单逐条对账，沉淀"失败模式库"。

## 第三部分 · 两方法联动

### 3.1 拿验收标准逐条问："漏了这条会不会死？"

| # | 验收标准 | 漏了会死吗 | 死的形态 | 挂靠 |
|---|---|---|---|---|
| 1 | 扫描 ≤ 5s | 不会死，但超 10s 必被嫌 | 慢性弃用 | T2 |
| 2 | 识别率 ≥ 80% | 半死 | 手改堆积 = 维护负担 | R2 / T2 |
| 3 | 手改 ≤ 1 行 / 30s | 半死 | 兜底成本高 = 直接弃用的路径 | T2 |
| 4 | 启动 ≤ 3s | 不会死 | 慢 → 回退旧习惯 | S2 |
| 5 | 零接入 | 半死 | 维护负担累积，最终不维护 | H1 |
| 6 | 组员 ≤ 30min | 死"共建叙事"，不死核心 | 仓库变独角戏 | R3 |
| 7 | 持续使用（每周 ≥ 3 次） | **这就是死亡判据本身** | —— | R1 / H1 |
| 8 | 推荐意愿 | 不死（自用核心可独立） | 只是传播线未建立 | S3 |
| 9 | 本体可生长 | 死"本体承诺" | 工作台退回一次性工具 | R5 / T1 |

**结论**：9 条里真正"会死"的是 №7（持续使用）与 №9（可生长）——它们不是指标，是生死判据；其余标准的作用是"防止慢性弃用"。

### 3.2 闭环与执行节奏

```
JTBD（1.x）：定义成功 → 9 条可衡量验收标准
        ↓
Pre-mortem（2.x）：7 项 ⚠️ + 8 项 ⚡ 预防措施
        ↓
开工清单（2.5 五件事）＋ 开发（每版本跑验收 checklist）
        ↓
监控：每周使用自测 + 里程碑重做 Pre-mortem
        ↓
上线 1 个月后：Post-mortem 对账 2.2 清单 → 沉淀失败模式库
```
