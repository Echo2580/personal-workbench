## 一、项目是什么

「个人工作台」是一个**功能聚合体**——不是某个具体问题的解决方案，而是"缺什么就往里加"的个人台子；每个人的工作台都不尽相同。

**第一个落地的功能（第一块拼图）：项目集中 + 启动器。** 解决痛点：学习/工作中的项目散落在各个文件夹，平时接触不到、存在感低，只能吃灰；想回顾时又要翻文件夹、回忆怎么跑，成本高到"回头看看"根本不会发生。做法：

- 自动扫描指定目录 → 散落的项目汇成一张清单
- 每个项目一条"启动配方"：跑命令 / 开 IDE / 开文件夹 / 开网页，点一下就走
- 配方大多自动识别（认得出 `main.py`、`package.json` 等特征），认不出的手改一行兜底

**项目的一句话灵魂**：成功不靠功能多，靠"回顾"真的发生；失败大概率不是被对手打败，而是死于"自己不用"。

## 四、已锁定决策（不得擅自更改）

1. **技术路线**：本地小管家——Python 常驻小服务 + 本地网页界面；扫描、启动都归服务管。（背景：与发起人的 FastAPI 学习线重合，可顺势而为。）
2. **启动器机制**：每项目多条"配方"（跑命令 / 开 IDE / 开文件夹 / 开网页）+ 一条主按钮；配方自动猜 + 手改一行兜底；启动后**放生**（不跟踪进程）。类比锚点：PyCharm Run Configuration。
3. **V1 边界（写死）**：扫描 + 清单 + 启动 + 手改兜底。就这些，多一点都不行。
4. **不做清单（写死）**：GUI 配置器 / 插件机制 / 云同步 / 非启动器功能。新想法一律进 Issue 排队，不进 V1。
5. **两层分析口径**：工作台本体（聚合体愿景）与第一块拼图（启动器切片）分开陈述——**严禁把项目窄化成"启动器工具"**（口径漂移风险 R5 已实际发生 2 次，属最高频风险）。
6. **生死判据（只有两条）**：① 上线后每周真打开 ≥3 次、且真启动过项目；② 之后新增功能只"挂接"、不改 V1 老模块。其余 7 条验收标准都只是"防慢性弃用"，不是生死项。
7. **关键数字基线**：扫描 ≤5 秒（100 项目量级）/ 配方自动识别率 ≥80% / 一键启动 ≤3 秒 / 新项目零接入 / 入口"双击即用"≤2 次操作。

## 六、协作规矩（必须遵守）

1. **git 提交由发起人本人执行**：你只提供命令语句（**PowerShell 语法**、注明用途），由发起人自己复制粘贴执行。不要直接调用 shell 执行 commit / push。（若你的服务对象不是发起人，请先与其确认协作方式。）
2. **改文件先告知、经同意再动**：未经发起人明确许可，不得修改其任何文件；要改动先说明"改什么、为什么改"，得到同意后动手。若发起人明确授权"直接改"，则按授权执行，并保持**增量修改**（一次一件事）+ **同步记录**（改了什么、为什么）。
3. **单线推进**：一次一个话题；前一步确认后再进下一步；不抢跑输出。
4. **区分"讨论阶段"与"执行阶段"**：发起人明确说处于讨论阶段时，禁止输出定稿方案 / 阶段表 / 路线图；只给判断与取舍理由，把决定权留给发起人。
5. **不替发起人拍板**：方案选择、优先级、是否开工——全部由发起人决定。
6. **记录与收尾主动补齐**：进度追踪、变更日志、commit message 建议等收尾工作由 AI 主动完成；发起人专注思考与决策。
